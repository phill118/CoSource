# Supervised operations

Operational corrections are append-only. A correction must supersede one active record with the same semantic binding and, for receipts and settlement evidence, the exact same external reference. Active truth is derived from the leaves of a non-branching supersession graph; historical records remain inspectable but do not contribute to receipt coverage or reconciliation.

Receipt corrections remain available after full receipt and reconciliation review. Coverage is recomputed from active decision-grade receipts, so reducing a corrected quantity can return a case to `partially_received` and revoke completion authority until exact coverage is restored. Persisted lifecycle labels are accepted only when ordered events and their bound records reconstruct the same legal state.

Each operational basis owns a bounded immutable snapshot of the canonical observation's complete offer-membership set, including each offer's merchant identity or explicit merchant absence. The operational line selects from that frozen set; it does not duplicate the selected offer as a second authority. A deterministic structural fingerprint detects accidental or coordinated persisted-field corruption, but is not authentication or cryptographic tamper-proofing. The snapshot keeps an observation structurally verifiable after normal evidence-history eviction, while current and retained observations must still agree exactly with the canonical ledger. Replay applies closed event-type bindings and the same state gates as commands, including exact-line handoff timing and the prohibition on ordinary post-receipt fulfilment.

CoSource owns a project-scoped operational case that records how a committed resource requirement and purchase plan progress after decision work. The application kernel is the only live mutation authority. A case is an auditable projection of canonical goal, evidence, plan, supplier, and cost owners; it is not a second owner for any of them.

## Authority boundary

Opening a case prepares a bound snapshot. Requesting approval does not approve it. Approval is an explicit human command and recomputes current plan readiness plus the exact decision basis. CoSource never treats stored readiness as continuing authority. Ordering, checkout, payment, licence acceptance, booking, and supplier communication happen outside CoSource. An external-action record only states that a human reports an outside action and retains its reference and evidence.

The lifecycle is closed: `draft` → `awaiting_approval` → `approved_for_handoff` → `externally_actioned`, followed by acknowledgement/fulfilment, receipt, reconciliation, and `completed`. Explicit rejection returns a request to draft. Explicit rebase returns a non-terminal case to draft while retaining its append-only history. `cancelled` and `completed` are terminal. Illegal transitions fail without mutation.

## Binding and staleness

Each case binds the workspace, requirement and revision, plan and revision, exact plan lines, quantities and unit semantics, selected product/offer/merchant identities, evidence observation IDs/sequences/times, applicable verification revisions, linked supplier revisions, supported expected-cost bounds, and an applied-scenario basis when present. Material changes make the case visibly stale. The human must explicitly rebase; current plans never silently rewrite historical cases.

Supplier contacts and quotations remain supplier-domain records. An acknowledgement that creates a contact updates supplier history and its case reference in one kernel commit. Expected cost is a bounded snapshot produced by canonical plan evaluation. Actual amounts use integer minor-unit money, remain currency-isolated, and carry represented time and evidence. Quotation and authorisation observations are never added to settlement. Referenced charge/refund transactions are additive, while a referenced total-payable observation is an independent snapshot; disagreement between the two is a conflict. Only decision-grade evidence can establish a conclusive reconciliation. Adding or correcting cost evidence immediately invalidates the stored result. Corrections append a record that explicitly supersedes one active record; history remains visible but only the active projection participates. Completion recomputes the canonical result instead of trusting the stored label. No FX or confidence percentage is invented.

Every outside handoff explicitly names one or more uncovered case lines, and the case does not advance to fully handed off until their union covers every line. A single real outside action can cover multiple selected lines. Mixed-merchant or mixed-supplier actions retain no arbitrary aggregate merchant/supplier identity; their exact line bindings remain authoritative. Once any handoff exists, its requirement, plan, line, evidence, supplier, and expected-cost basis is immutable; later changes remain visible as historical staleness rather than an invitation to rebase. Fulfilment observations are line-bound facts and must follow the handoff for that exact line. Quantities are positive safe integers, and contradictory or excessive quantities are rejected rather than clamped. Receipt observations have exact references and support append-only supersession. Receipt is complete only when active decision-grade observations exactly cover every resolved line quantity. Exceptions remain visible until explicitly resolved. Completion requires complete receipt coverage, a current supported reconciliation, and no open high/critical exception.

## Durability and agent access

Operational cases participate in the existing version-one workspace envelope and compare-and-save fingerprint. Older version-one records restore with an empty case collection. Strict parsing checks project, goal, plan, observation, supplier, line, event, approval, and reference bindings. Saved projects remain isolated; restoration performs no provider request and adds no clearing, deletion, or merge authority.

The existing `get_purchase_plan` WebMCP read includes bounded operational summaries. There are still exactly 13 tools and no operational mutation, communication, checkout, payment, order, booking, or storage tool. Live connectors that could perform external work remain deferred.
