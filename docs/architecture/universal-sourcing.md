# Universal sourcing

CoSource owns one provider-independent sourcing spine. A strict `ResourceRequirement` is copied into a bounded, transient sourcing request without creating another editable requirement identity or revision. The application-level `SourceRegistry` validates declarations, rejects duplicate source IDs, and orders sources deterministically. `SourcingCoordinator` negotiates capabilities and compiles source legs before any network access.

Source and resource kinds are bounded strings so future materials, services, software, licensed assets, equipment, suppliers, and fulfilment sources can be registered without a kernel category switch. A declaration states factual capabilities: resource types, executable search and inspection operations, pagination, market dimensions, hard-filter versus soft-preference versus negative-filter semantics, supported operators and normalized fields, quantity, availability, cost, freshness, compatibility, licensing evidence, and hard limits. Source legs are ordered by executable search, fewer mandatory limitations, requester preference among mandatory-equivalent sources, fewer preference limitations, and finally stable source ID. Preferred sources therefore never outrank materially more capable sources, win a product decision, or become capable by preference. Excluded and unsupported sources are never called. Field matching trims and lowercases deterministically, with the documented `colour` to `color` alias at one explicit boundary; it never uses fuzzy matching.

Every plan identifies the canonical requirement and revision, market, result limit, selected source legs, projected inputs, constraints actually transmitted, per-leg limitations, globally unresolved mandatory and preference gaps, warnings, and deterministic selection reasons. Required constraints have projection priority; preferences cannot become hard filters and exclusions cannot become positive filters. Overflow and query limits remain explicit and are never described as applied or silently truncated. Capability metadata is not evidence and cannot revise a goal, evidence ledger, comparison, plan, proposal, or approval.

Candidates have source-scoped identity, resource type, bounded display data, retrieval provenance, explicit `untrusted_external_data` classification, bounded facts, and inspection/refresh references. Strict output validation enforces collection and message limits, source/provenance binding, unique identities, continuation context, safe estimated totals, and rejects unknown canonical output fields. They contain no raw provider envelope and do not impose retail offers on non-commerce resources. For purchasing, this is a computed envelope over the detailed canonical `ProductCluster`; a generic coordinator is type-bound to its specialised candidate, so non-product results cannot enter the purchasing workspace. The projection is transient and never duplicates the product evidence ledger.

The current production source adapter is Shopify Global Catalog through the existing browser catalogue client and server gateway. It implements product search and inspection through the existing catalogue port, plus pagination, country/currency market context, availability, exact unit-cost filtering, and only required hard equality filters for supported taxonomy fields. It does not claim soft preference, negative filtering, ranking, or boosting. Provider provenance maps exactly to source explicit, source inferred, CoSource derived, or unknown. Shopify schemas, credentials, transport, mapping, and public-response validation remain at their existing adapter and gateway boundaries. There is no second Shopify mapper or browser-to-provider route.

Human and agent discovery share the coordinator while retaining independent latest-request authority. Continuations are bound to source, requirement ID and revision, channel, and request criteria before reuse. The agent workspace remains capped at ten candidates. Search results, plans, source instances, cursors, failures, and loading state remain transient; IndexedDB stays at version 2 and workspace envelopes at format 1.

R5R2 binds each neutral candidate to its specialised candidate through the registered source's bounded identity resolver. Equal array lengths are insufficient: every position must resolve to the same source-scoped identity, and canonical or specialised duplicates, reordering, resource-type mismatches, excess results, contradictory trust, and impossible inspection or pagination claims are rejected before state mutation.

Generic multi-source execution is deliberately all-or-nothing. A failed leg raises an error carrying that leg's source ID, so partial results cannot become accidental application state. The purchasing application uses the smaller truthful boundary: it explicitly selects the first capability-ordered executable source before network access, or the single owner named by a validated continuation. Its returned execution plan is rebuilt around that one leg, including only that source's mandatory gaps, preference gaps, result limit, applied constraints, reasons, and warnings. Thus one result limit governs one provider call and `hasMore` is never exposed without a usable source-bound continuation. Multi-source pagination is not claimed.

Product inspection and retained-evidence refresh resolve the candidate's provider identity to one uniquely registered provider binding that supports products, declares inspection, and supplies the validated inspection operation. Missing, incompatible, ambiguous, or non-inspectable ownership returns a bounded `evidence_unavailable` failure before provider access, evidence retention, refresh allocation, or any session mutation. The application kernel contains no hard-coded Shopify inspection fallback; the current Shopify adapter remains merely the registered production owner.

CoSource remains recommendation-only. Search, preferences, and negotiation cannot select a winner or execute checkout, payment, ordering, booking, licensing acceptance, or subscription activation. Reliability scoring, landed cost, ranking, optimisation, substitution, repair, monitoring, background jobs, and additional live providers remain later work.
