# Local workspace persistence

The application layer owns a replaceable `WorkspacePersistencePort`. The live CoSource application kernel remains the only state authority; persistence receives an explicit durable projection and can restore that projection once, atomically, into the kernel. The browser adapter implements the port with IndexedDB database `cosource-local-workspace`, version 1, store `workspaces`, and exact key `current`. A future authenticated repository can replace this adapter without moving storage concerns into domain models.

Format version 1 stores the stable workspace identity, saved durable revision and timestamp, market, goal draft, separately committed active goal, bounded canonical evidence ledger and history, comparison identities, purchase plan and bindings, bounded interpretation and plan proposals, and bounded activity. Money remains exact safe integer minor units and identities remain provider-scoped. Runtime validation is strict at every represented level, rejects unknown format versions and properties, and enforces the 50-subject, five-history-entry, 20-proposal, 20-activity, quantity, identity, timestamp, revision, uniqueness, and binding limits.

Discovery candidates, cursors, request identifiers, authority counters, loading and provider-error states, refresh lifecycle, React state, listeners, promises, WebMCP registration, and other execution state are transient. Restoration always creates idle human and agent discovery workspaces and empty refresh lifecycle. It never calls the commerce provider or automatically refreshes evidence.

The browser starts in `restoring` and does not expose the temporary fresh kernel to React controls or WebMCP. A valid record publishes one coherent restoration. With no record, the fresh workspace is saved and becomes ready. Durable fingerprints prevent semantic no-ops and transient changes from writing. Writes are serialized; rapid changes advance a dedicated durable revision and the newest projection eventually wins. IndexedDB compare-and-save checks the expected persisted revision in the same read-write transaction, so a stale tab enters an explicit conflict state without overwriting either its memory state or the newer record.

Save failure preserves current memory state and allows retry of the newest projection. A transient IndexedDB open/load failure is shown as memory-only operation with an explicit safe retry. If the environment has no IndexedDB implementation, the composition root marks retry unsupported and the interface gives an honest memory-only status without a no-op control. Corrupt or incompatible records remain untouched and automatic saves stay disabled. Initial corrupt restoration gates an uninitialized workspace. If corrupt data is discovered only after a human has changed the memory-only workspace, the controller marks that memory as preserved: the human workspace remains visible with a prominent retryable warning, while WebMCP and saving remain disabled. R3 intentionally provides no destructive reset operation.

The controller records a durable fingerprint at the instant an initial read becomes unavailable. A later retry reconciles against that boundary before doing anything: unchanged memory may restore a valid record or initialize an absent record; changed memory may initialize only genuinely absent storage through compare-and-save. A valid recovered record alongside changed memory is a conflict. Corrupt or incompatible recovered data requires recovery. Both outcomes preserve the in-memory workspace and the stored bytes. Concurrent retries share one operation, so recovery cannot duplicate subscriptions or initial writes, and save-error retry still persists the newest durable projection.

The IndexedDB adapter validates the current stored revision before using it for compare-and-save. Missing records with an expected revision conflict, and malformed revisions fail without creating a revision or overwriting data. The read, comparison, and write remain in one `readwrite` transaction. Each operation closes its database connection; a connection delivered after an already rejected blocked open is also closed. The adapter has no database, store, or record deletion authority. Direct adapter acceptance uses `fake-indexeddb` as a development-only, in-memory implementation of the browser API; it is not a production dependency.

Automated acceptance covers persistence/WebMCP ordering and the IndexedDB adapter contract, while production HTTP smoke covers the built application boundary. A native-browser IndexedDB save-and-reload acceptance was not recorded in R3R because no browser runtime was available; the in-memory adapter test is not represented as native-browser evidence.

This is local-device persistence, not an account, organisation, tenant, cloud backup, or cross-device service. Browser storage can be deleted by the user or browser and is not encrypted by CoSource independently of the browser profile. No credentials, environment data, checkout state, payment data, provider envelopes, or executable instructions are stored. Multiple saved-project UX, remote synchronization, merge resolution, and server persistence remain future work.
